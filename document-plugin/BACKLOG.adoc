== Vision Produit

Un plugin Gradle N2 qui **cree du contenu AsciiDoc assiste par IA**
et le **publie dans tous les formats supportes par AsciidoctorJ**
(HTML5, PDF, EPUB3, DocBook 5, ManPage), sans sortir du pipeline Gradle.

Le plugin couvre deux missions complementaires :

1. **Generation IA** → un LLM (gpt-oss:120b-cloud) assiste la redaction
   de documentation, specs, manuels, rapports en AsciiDoc structure
2. **Publication multi-format** → chaque backend AsciidoctorJ est expose
   comme une tache Gradle isolee avec configuration fine

=== Domaine « Book » (structuré, mise en page, logique)

Au-dela de l'assemblage plat (DOC-11), document-gradle porte un *domaine
« Book »* de premier rang : un agregat DDD `BookTree` qui organise le contenu
AsciiDoc en **arbre propre** — Parties → Chapitres → Sections → Sous-sections
— derive de la table des matieres (ref `1.0.2.6.4` = profondeur 4). Ce domaine
rend le livre (1) **architecturé** (hiérarchie restituee en niveaux `==`/`===`/
`====`), (2) **mise en page** (front/body/back matter, sauts de page, page de
titre, `:toc:`), (3) **logique** (numérotation hiérarchique, navigation
précédent/suivant, ancres de reference croisée). Voir EPIC `DOC-BOOK-DOMAIN`
(cadrage S-211, `CADRAGE_EPIC_DOC_BOOK_DOMAIN.adoc`). Consommateur pilote :
`office/metiers/FPA` (livre FPA II scanné → livre PDF/EPUB navigable).

== EPIC DOC-TRANSLATE — Pipeline de traduction AsciiDoc (refacto transverse bakery→document)

_Cadré Session 021 (2026-07-19). Document est le bounded context naturel pour toute
manipulation d'AsciiDoc (parse, traduire, convertir, enrichir). Bakery n'a pas
vocation à maintenir un AST AsciiDoc — il devrait le consommer._

[CAUTION]
====
**Motivation** : bakery-gradle contient un pipeline de traduction AsciiDoc complet
(`PivotModel` AST, `AsciiDocParser`, `ContentTranslationService`, `PlantUmlTranslationAdapter`,
`SubtreeI18nPlanner`, `I18nDeltaApplier`) qui n'a rien à voir avec le métier de bakery
(site statique JBake). Ce code devrait appartenir à document-gradle (WRITE + TRANSLATE +
CONVERT + PUBLISH), le bounded context naturel pour la manipulation d'AsciiDoc.

**Bénéfices** :
. Document = single source of truth pour la manipulation d'AsciiDoc
. Réutilisation cross-borough : magic-stick, cccp.education, talaria peuvent traduire sans bakery
. Bakery allégé, recentré sur son vrai métier : site statique JBake
. Boundary claire : Document = WRITE + TRANSLATE + CONVERT + PUBLISH

**DAG** : bakery → document (nouvelle dépendance `implementation`)
====

|===
| Artefact bakery | Destination document | Lignes | Tests
| `PivotModel.kt` | `document/translation/PivotModel.kt` | 95 | 20 UT
| `AsciiDocParser.kt` | `document/translation/AsciiDocParser.kt` | 412 | 30 UT

== ✅ EPIC DOC-CR5 — Conversion Security Policy (TERMINÉ, Session 222)

__source_ : suite directe de DOC-CR3-2 (safeMode) + DOC-CR4 (includeGuard).
_focus_ : cohérence de la combinaison `SafeMode` × `includeGuard` (défense en profondeur).
_statut_ : DOC-CR5-1 ✅ TERMINÉ (S-222, TDD strict 12 UT), DOC-CR5-2 ✅ TERMINÉ (S-222,

**Motivation** : DOC-CR4 audite les directives `include::` (vecteur de traversal), mais

. Fail-fast STRICT : pas d'illusion de sécurité (build refuse une config asymétrique).
. Visibilité LENIENT : l'asymétrie est signalée.

== ✅ EPIC DOC-XREF-VALIDATE — Validation des références croisées AsciiDoc (TERMINÉ, Session 224)

== Pièges Gradle à retenir (S-232..S-241)

1. *Snapshot collect* : `collectDocumentRetrieve` re-scan à chaque exécution
   (`outputs.upToDateWhen { false }`) — pas de `@InputFile` du rapport.
2. *mustRunAfter inverse la CLI* : conflit d'inputs si 2 tâches partagent
   un build.
3. *Chaîne N3 staged* : produce → validate → collect (3 builds).
4. *Property DSL sans convention reste unset même derrière `.orElse(...)`*.
5. *Dérivation knob sans dépendance de tâche* : jamais provider vers
   `outputFile` du producteur, jamais `.get()` configuration-time.
6. *`@InputFile` valide l'existence AVANT l'action* — porter les chemins
   audités en `@Input @Optional Property<String>` (pattern `htmlFilePath`
   / `epubFile`).
7. *`--tests` Gradle ne réduit PAS la découverte Cucumber* — filtrer côté
   annotation du runner (`FEATURES_PROPERTY_NAME`).
8. *Imports DSL consommateur* (S-239, documenté S-241) : les enums des
   gardes ne sont pas résolus implicitement — importer explicitement côté
   `build.gradle.kts` tiers. Liste dans README.md.
9. *epubcheck callback Java → null* : `info(feature, ...)` reçoit null —
   signature nullable obligatoire côté Kotlin (NPE sinon).
10. *Preuve négative epubcheck* (S-241) : le flip d'octet naïf est TOLÉRÉ
   (zip toujours lisible) — corrompre la STRUCTURE (supprimer lentrée
   `mimetype` non compressée, première entrée OCF obligatoire) pour
   déclencher `Invalid`.

== Anti-glue Cucumber (règle de propriété — S-238)

Chaque feature a UN runner propriétaire. Le runner global (glue
`document.scenarios`) ne découvre que `document.feature` +
`release-notes.feature` + `frontmatter_retranslate.feature`. Toute
nouvelle feature doit soit rejoindre un runner dédié (pattern : runner + glue + tag + CucumberTaskSpec dans build.gradle.kts), soit
explicitement rejoindre le global avec ses steps dans `document.scenarios`.
Le 17e runner dédié est `epubCheckCucumberTest` (S-240).

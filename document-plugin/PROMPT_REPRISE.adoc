== Pièges Gradle à retenir (S-233/234/235/236)

1. *Snapshot collect* : `collectDocumentRetrieve` doit re-scanner à chaque
   exécution (`outputs.upToDateWhen { false }`) — un `@InputFile` du rapport de
   validation est impossible car `bookPipeline` dependsOn collect pendant que
   le rapport n'existe pas (piège S-232 #3).
2. *mustRunAfter inverse la CLI* : `validateDocument.mustRunAfter(collect)`
   inverse la chaîne CLI `validateDocument collectDocumentRetrieve` (le collect
   tournerait d'abord → n/a). Le conflit d'inputs (outputDir couvre le
   book.adoc) n'existe que si les 2 tâches partagent un build.
3. *Chaîne N3 staged* : produce → validate → collect (3 builds dans le FT
   dogfooding) — un cycle Gradle interdit l'ordre métier en un seul build.
4. *Property DSL sans convention reste unset même derrière `.orElse(...)`* :
   `cliProp(...).orElse(ext.x)` produit un provider unset si aucune branche
   n'a de valeur → `Value not set` à l'exécution (piège S-234).
5. *Dérivation knob sans dépendance de tâche* (S-235) : pour pointer l'output
   d'une tâche, dériver le chemin du MÊME knob (layout + knob flatMap),
   jamais un provider vers `outputFile` du producteur (dépendance implicite) ;
   jamais `.get()` configuration-time (`Querying the mapped value...`).

== Anti-glue Cucumber

Un texte de step identique dans 2 classes → `DuplicateStepDefinitionException`
(S-223). Le runner *global* (glue `document.scenarios`) ne voit pas les steps
des runners dédiés (autres packages) → `UndefinedStepException` pour les
features hors glue. Comparer baseline via `git stash` pour isoler l'impact
d'un fix (méthode S-234). Attention aux *faux positifs d'assertion* : un
fragment de message partagé par 2 findings distincts fait passer un test pour
la mauvaise raison — choisir des fragments discriminants (S-235).

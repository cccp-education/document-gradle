= Session 211 — Cadrage EPIC DOC-BOOK-DOMAIN (Domaine « Book » structuré)

_Borough_ : document-gradle (New Orleans 🟢)
_Date_ : 2026-08-27
_Type_ : cadrage (gouvernance pure, zéro code modifié)
_Score_ : 10/10

== Objectif

Cadrer le domaine « Book » dans document-gradle pour organiser le contenu
AsciiDoc en *arbre propre* : (1) architecturé (hiérarchie Parties→Chapitres→
Sections dérivée de la TOC), (2) mise en page (front/body/back matter, sauts
de page, page de titre, `:toc:`), (3) logique (numérotation, ancres, navigation).
Consommateur pilote : `office/metiers/FPA` (livre FPA II scanné).

== Constats audités (8)

1. `BookAssembler.assemble` produit un blob plat (header + concaténation),
   aucun niveau de section `==`/`===`.
2. `BookSection` est plat — la hiérarchie encodée dans `ref` (`\d+(\.\d+)*`)
   est ignorée.
3. La TOC FPA encode 4+ niveaux (`1.0.2.6.4`) — modèle plat incapable.
4. Aucune notion de `Matter` (front/body/back).
5. Aucune logique de navigation (numérotation, ancres, précédent/suivant).
6. `BookValidator` valide la cohérence page↔TOC, pas la structure.
7. FPA-BOOK-4 (`bookPipeline`) attend un livre navigable — blob plat bloque
   la validation humaine du rendu.
8. `BookAssembler` est un `object` pur → refactorable par surcharge
   (compatibilité préservée).

== Décisions architecturales (10)

Agrégat `BookTree` de premier rang ; hiérarchie dérivée du `ref` (profondeur =
nb segments, parent = préfixe) ; `BookNode` value object ; `Matter` classifier
(FRONT/BODY/BACK, convention `0.x`/`1..n.x`/`9.x` + fallback explicite) ;
`BookLayout` value object (niveaux, sauts de page, page de titre + `:toc:`) ;
refactor `BookAssembler.assemble(tree, layout)` par surcharge ; `BookNumbering`
(numérotation/ancres/nav) ; extension `BookValidator` sur l'arbre (lenient/
strict) ; baby-step DDD/TDD/BDD strict ; frontière licence préservée.

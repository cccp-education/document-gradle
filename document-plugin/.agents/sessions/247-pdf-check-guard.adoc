== Constat réel dogfooding (à retenir)

*PDFBox 3.x est ultra-lénient sur les dommages binaires* :
- fichier tronqué (xref manquant) → **charge quand même** (reconstruction xref) ;
- header corrompu (garbage dans les 26 premiers octets) → **WARNING**
  « Header doesn't contain versioninfo » + charge quand même (15 pages) ;
- seul un fichier sans structure parsable échoue (`<pdf-load-failed>`).
Leçon miroir du piège EPUB #10 : la preuve négative PDF doit corrompre la
*signification métier* (pages sans texte extractible), pas les octets.
Le garde PDF est donc surtout un garde *texte extractible par page* (le
check load/pages reste utile pour les fichiers vraiment cassés).

== Pièges découverts (à retenir)

1. `PDPageContentStream.setFont(PDFont, float)` — 2 params obligatoires en
   PDFBox 3.x (l'erreur `No value passed for parameter 'p1'` Kotlin vient du
   size manquant, PAS de la résolution du constructeur `PDType1Font(FontName)`).
2. PDFBox tolère header corrompu + xref tronqué (warnings) — voir constat
   dogfooding ci-dessus.
3. L'enum nested se référence proprement via
   `import org.apache.pdfbox.pdmodel.font.Standard14Fonts.FontName`.

:epic: DOC-BOOK-DOMAIN

:session: 211
:pattern: S-057/S-063 (gouvernance pure) + baby-step DDD/TDD/BDD
:consommateur: office/metiers/FPA (livre FPA II scanné)

== Contexte

_Leçon pilote_ : le pipeline livre (DOC-11 `assembleBook` + DOC-BOOK-VALIDATE)
assemble aujourd'hui les pages OCRisées (codex/codebase) en **un blob AsciiDoc
plat** : un en-tête `= Titre` + `:author:`, puis la concaténation des pages dans
l'ordre `PageOrder`. La table des matières source (`Devenir_..._FPA_II.adoc`,
~180 sections) encode pourtant une **hiérarchie profonde** par son `Référence`
(`1.0.1`, `1.0.2.6.4`, `2.1.5`…) — un livre à parties, chapitres, sections,
sous-sections, annexes.

Ce blob plat est *illisible et non-navigable* : aucun `==`/`===` n'apparaît,
le lecteur ne peut pas sauter à une section, la numérotation est absente, le
glossaire/index/préface (matter) ne sont pas distingués du corps. Or AsciiDoc
`doctype: book` *attend* une structure en arbre (level-0 titre, puis parties
`==`, chapitres `===`, sections `====`, back matter). L'assemblage plat
casse la promesse du format et empêche une vraie publication PDF/EPUB navigable.

_L'objectif de cet EPIC_ est de **cadrer le domaine « Book »** comme un agrégat
DDD de premier rang dans document-gradle : un *arbre propre* qui organise le
contenu AsciiDoc de manière (1) **architecturée** (hiérarchie Parties→Chapitres→
Sections dérivée de la TOC), (2) **mise en page** (front/body/back matter, sauts
de page, page de titre), (3) **logique** (numérotation hiérarchique, navigation
précédent/suivant, ancres de référence croisée). Le contenu FPA (données de
scan) reste dans `office/`, le domaine et ses tests vivent en Apache 2.0 dans
document-gradle.

== Décisions architecturales

. *Agrégat `BookTree` de premier rang* — le domaine « Book » devient un
  agrégat DDD : racine `BookTree` contenant des `BookNode` (arbre
  Parties→Chapitres→Sections→Sous-sections→…), une `Map<ref, BookNode>`, et
  la liste ordonnée des feuilles (pages). C'est la *source de vérité
  structurelle* du livre, découplée de l'assemblage.

. *Hiérarchie dérivée du `ref`* — la profondeur d'un nœud = nombre de
  segments du `ref` (`1.0.2.6.4` → level 4). Le parent d'un nœud = préfixe
  tronqué au segment k-1 (`1.0.2.6` → parent de `1.0.2.6.4`). `BookTreeBuilder
  .fromSections(List<BookSection>)` reconstruit l'arbre ; `BookSection` existant
  devient la *feuille source* (mapping ref→page). Zéro changement de format TOC.

. *`BookNode` sealed/value object* — `BookNode` = data class immuable
  (`ref, title, level, children: List<BookNode>`, + `sourcePage` pour la feuille
  mappée). Pas de dépendance Gradle. TDD strict (15 UT : dérivation profondeur,
  lien parent, unicité ref, ordre, refs orphelins).

. *`Matter` (FRONT/BODY/BACK)* — classifier logique d'un nœud selon la racine
  de son `ref` OU un marqueur explicite dans la TOC. Convention proposée :
  `0.x` → FRONT (préface, intro, TOC), `1..n.x` → BODY (corps), `9.x` → BACK
  (glossaire, index, annexes). `Matter` est une value object du domaine, testable
  sans I/O.

. *`BookLayout` (mise en page)* — value object portant la stratégie d'émission
  AsciiDoc : niveau de section par profondeur (`==` pour level 1, `===` level 2,
  …), politique de saut de page (`<<<` ou `:page-break:`), émission de la page
  de titre et de la TOC (`:toc:`), placement du front/back matter. DDD pur,
  testable (émet une `String` AsciiDoc attendue).

. *Refactor `BookAssembler` par surcharge* — nouvelle `assemble(tree, layout)`
  émet header + front matter + corps (sections imbriquées aux bons niveaux) +
  back matter. L'ancienne `assemble(pagesDir, title, author, photosDir)`
  reste pour compatibilité (blob plat). Non-régression : `BookAssemblerTest`
  existant reste VERT.

. *`BookNumbering` (logique)* — value object calculant la numérotation
  hiérarchique (`1`, `1.2`, `1.2.1`…), les ancres de référence croisée
  (`[[ref]]`), et la navigation précédent/suivant. DDD pur, testable (10 UT).

. *Extension `BookValidator` sur l'arbre* (US-6, option) — règles structurelles
  : continuité des `ref` (pas de trou de niveau), unicité des `ref`, présence
  d'au moins un nœud FRONT et un nœud BACK, monotonicité de l'ordre de page.
  Mode lenient/strict réutilisé (DOC-BOOK-VALIDATE).

. *Baby-step DDD/TDD/BDD strict* — RED → GREEN → REFACTOR, 1 fichier à la
  fois, 3 niveaux (unit / functional / Cucumber). English only dans le code.
  Chaque US est *testable isolément* avant le refactoring de l'assemblage.

. *Frontière licence préservée* — le domaine et ses tests sont Apache 2.0
  dans document-gradle ; les données FPA (pages/scans/TOC) restent dans
  `office/metiers/FPA/`. On prend des morceaux du livre FPA pour dogfooder,
  jamais l'inverse.

== Modèle du domaine (vocabulaire ubiquit)

----
Book (agrégat racine, doctype: book)
 ├─ frontMatter : List<BookNode>   (Matter.FRONT  — préface, intro, TOC)
 ├─ bodyMatter  : List<BookNode>   (Matter.BODY   — parties/chapitres/sections)
 ├─ backMatter  : List<BookNode>   (Matter.BACK   — glossaire, index, annexes)
 └─ leaves      : List<BookSection> (pages OCR, mapping ref→page, source de vérité contenu)

BookNode (value object)
 ├─ ref      : String   (ex "1.0.2.6.4")
 ├─ title    : String
 ├─ level    : Int      (= nb de segments du ref)
 ├─ matter   : Matter
 ├─ children : List<BookNode>
 └─ source   : BookSection?  (feuille mappée sur une page OCR)

BookTreeBuilder.fromSections(List<BookSection>) : BookTree
BookLayout.emit(tree) : String   (AsciiDoc structuré navigable)
BookNumbering.compute(tree) : Map<ref, NavEntry>  (numéro + prev/next + anchor)
----

== Relation avec FPA (consommateur)

* FPA-BOOK-4 (`bookPipeline`) **consommera** `BookTree` + `BookLayout` pour
  produire un livre PDF/EPUB *navigable*. Le cadrage DOC-BOOK-DOMAIN est la
  pré-condition de FPA-BOOK-4 (le blob plat rendait la validation humaine
  impossible).
* Ajout côté FPA d'une US *FPA-BOOK-5 « Book tree structured assembly »* qui
  dogfoode `assembleBook(tree, layout)` sur le `livre.adoc` FPA réel une fois
  DOC-BOOK-DOMAIN-3 livré. Voir `office/metiers/FPA/BACKLOG.adoc`.

== Gates et risques

* *Gate* : aucune dépendance cross-borough bloquante. `BookSection` existant
  est réutilisé (mapping ref→page). Le domaine est autonome (zéro import codex).
* *Risque* : TOC FPA non parfaitement monotone (refs `1.0.2` puis `1.0.2.1`)
  — `BookTreeBuilder` doit tolérer l'insertion de nœuds feuilles hors ordre
  strict (arbre reconstruit depuis le `ref`, pas depuis l'ordre de ligne).
* *Risque* : matter FRONT/BACK par convention `0.x`/`9.x` peut ne pas coller
  à la TOC réelle FPA — classifier configurable (marqueur explicite dans la
  TOC en fallback). Pas de hardcode aveugle.
* *Non-régression* : ancienne `assembleBook` (blob plat) conservée ; les
  tests DOC-11/DOC-BOOK-VALIDATE existants restent VERTS.
* *Économie d'encre* : l'arbre est dérivé du `ref` déjà calculé — zéro
  re-OCR, zéro nouvel I/O coûteux.
